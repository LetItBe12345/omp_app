# OMP Desktop 面试问答树

这份文档按一次 20～40 分钟的项目深挖整理。回答时不要把所有细节一次说完。先给结论和实现事实，面试官继续追问时，再进入对应分支。

## 一、项目速答：面试官先让你介绍项目

### 问题

你介绍一下这个项目，以及你主要解决了什么问题？

### 建议回答

这是一个面向本地项目的 OMP Agent Desktop，运行在 Ubuntu 上。它不是完整 IDE，而是把 Workspace、文件树、Agent 会话、流式输出和权限确认放进一个 Electron 窗口。

技术上使用 Electron、React、TypeScript，通过 OMP 的 `--mode rpc` 接入已有 Agent 能力。整体链路是：React Renderer 负责界面，Preload 暴露受控 API，Electron Main 负责窗口、文件、状态和 Runtime 生命周期，OMP Runtime 通过 stdin/stdout 传输 JSONL RPC。

项目中比较有挑战的部分有三个：一是桌面进程和 Agent Runtime 的生命周期管理；二是把乱序、重复、增量的流式事件投影成稳定的对话 UI；三是 Linux 图形启动时的环境、代理、Wayland、GPU 和打包兼容性。

### 继续追问：为什么不直接做成 Web 应用？

答题要点：

- 目标是本地项目。Workspace 路径、文件树、Runtime 子进程和本地权限都需要桌面能力。
- OMP Runtime 是本机二进制，使用 stdin/stdout RPC，Electron Main 更适合管理它的启动、停止、环境和日志。
- Electron 可以把 Chromium UI 和 Node/系统能力分开，Renderer 不直接接触文件系统和子进程。

### 继续追问：为什么不做成完整 IDE？

答题要点：

- 产品范围明确是 Agent Desktop，不复制 VS Code 的编辑器、调试器和插件市场。
- MVP 只做文件浏览、上下文引用和外部打开路径，文件编辑、Changes/Diff、Terminal 属于后续能力。
- 缩小范围后，主要精力可以放在 Agent 运行链路和交互稳定性上。

### 继续追问：项目目前哪些能力还没有做？

答题要点：

- Changes / Review / Diff 面板。
- 应用内文件预览和编辑。
- Browser Use、独立代理环境和 Wayland Computer Use。

当前已支持多会话并行。每个正在生成的 Session 对应一个 OMP Runtime，超出最大并行数的任务进入全局 FIFO 队列。

## 二、总体架构与进程边界

### 问题 1：为什么采用四层结构？一次消息是怎么走的？

### 建议回答

四层分别是 Renderer、Preload、Main 和 OMP Runtime。

用户在 Renderer 输入消息后，通过 Preload 暴露的 `prompt` API 调用 Electron IPC。Main 校验当前 Workspace、Session 和运行状态，再把 RPC frame 写入 OMP Runtime 的 stdin。Runtime 从 stdout 输出 JSONL 事件，Main 解码后通过 IPC 发回 Renderer。Renderer 的 reducer 消费事件，生成对话投影并渲染。

这样分层的原因是权限边界清楚：Renderer 只处理 UI，Main 才能访问本地文件、启动子进程和保存状态；OMP 继续负责 Agent Loop、模型请求和工具执行，Desktop 不重新实现这些能力。

### 继续追问：为什么不能让 Renderer 直接调用 RPC？

答题要点：

- Renderer 不应该持有子进程句柄，也不应该直接访问 stdin/stdout。
- 直接开放 Node 能力会扩大 XSS 或恶意页面拿到本地权限的影响范围。
- Main 需要统一检查 Workspace、Session、运行状态、请求参数和权限状态。
- Preload 只暴露 `DesktopApi` 中的明确方法，不暴露通用 `ipcRenderer.send` 或 Node API。

### 继续追问：Preload 的作用是什么？

答题要点：

- 在 `contextIsolation` 边界上提供窄接口。
- 把 `ipcRenderer.invoke` 封装成有类型的业务方法，例如 `prompt`、`switchSession`、`stopCurrentRun`。
- 把事件监听的取消函数返回给 Renderer，避免组件卸载后继续收事件。
- 类型定义集中在 `src/shared/desktop-api.ts`，Main、Preload、Renderer 共用数据结构。

### 继续追问：OMP Runtime 负责什么，Desktop 负责什么？

答题要点：

| OMP Runtime             | Desktop                        |
| ----------------------- | ------------------------------ |
| Agent Loop              | 窗口和 UI                      |
| 模型调用                | Workspace / Session 展示和选择 |
| Bash 等 Agent Tool      | Runtime 启停、环境和日志       |
| Provider 登录和凭据管理 | 文件树、上下文候选和本地状态   |
| RPC 协议事件            | 权限交互转发和安全校验         |

核心原则是复用 OMP 的 Agent 能力，不在 Desktop 中复制一套模型、工具和会话系统。

### 继续追问：如果 OMP Runtime 崩溃，用户界面怎么处理？

答题要点：

- Main 监听 `spawn` 的 `error`、`exit`、stderr 和协议错误。
- Runtime 状态变为 `failed` 或 `stopped`，保存可诊断的错误和日志路径。
- Renderer 收到状态事件后停止发送、显示重启或恢复入口，而不是继续假设 Runtime 可用。
- 重启时重新建立 stdin/stdout 监听，并恢复当前 Workspace 和 Session。
- 退出时按正常等待、SIGTERM、SIGKILL 的顺序清理，检查没有遗留 OMP 进程。

## 三、Runtime 生命周期与并发控制

### 问题 2：Runtime 是怎么启动和切换的？

### 建议回答

首次提交任务时，Main 根据目标 Workspace 的 `cwd`、Runtime 路径、Session 网络和解析后的环境向 Runtime Pool 申请进程。Runtime 参数是 `--mode rpc`。Runtime 进入 `ready` 后，Main 再读取状态、模型、命令和历史消息。

正在执行的 Runtime 继续绑定原 Session，切换当前界面不会停止它。新任务优先复用同 Workspace 且环境、网络和权限相容的空闲 Runtime；没有相容进程时再启动新 Runtime。达到并行上限时进入等待队列。

### 继续追问：为什么 Workspace 打开不能等 Runtime ready 后再显示？

答题要点：

- 目录选择器返回后，Workspace 可以先持久化并显示。
- Runtime 启动受系统目录选择器、Shell、代理和 OMP 状态影响，等待它会让 UI 感觉卡住。
- 设计上把“显示 Workspace”和“后台启动 Runtime”拆成两个阶段。
- UI 先显示等待或连接状态，Runtime ready 后再允许发送任务。

### 继续追问：如何避免切换 Workspace 时旧 Runtime 的事件污染新 Workspace？

答题要点：

- Runtime Pool 为每次 Session 租约分配 Runtime Instance ID 和 generation。
- RPC 响应、流式事件、Tool Approval 和 Extension UI 都核对 Workspace ID 和 Session ID。
- 相同的原始 RPC ID 还要与 Runtime Instance ID 和 generation 组成复合键，防止不同进程或重启前后串事件。
- IPC 处理器根据请求显式携带的目标 Session 路由，不使用“当前可见 Session”作为隐式条件。
- 测试覆盖切换和重启过程中的状态恢复，不能只测试正常启动。

### 继续追问：为什么一个正在执行的 Session 要占用一个 Runtime？

答题要点：

- OMP 的 `prompt` 使用进程内当前 AgentSession，单个 Runtime 不能安全地同时执行两个 Session。
- 独立进程可以隔离 stdin/stdout、请求 ID、工具审批和崩溃影响。
- 进程和内存成本通过 1–10 的最大并行数、FIFO 队列、空闲复用和定时回收控制。

### 继续追问：运行中用户再次发送消息怎么办？

答题要点：

- 普通消息进入 Follow-up 队列，按发送顺序逐条执行。
- 运行期间发送按钮变为 Stop，模型和 Thinking 等级不能切换。
- Stop 会结束当前任务并清空 Follow-up；当前被中止的用户消息放回输入框。
- MVP 不做 Steer，避免同时修改当前 Agent Loop 的输入语义。

## 四、RPC、JSONL 和流式事件

### 问题 3：JSONL RPC 的难点是什么？

### 建议回答

难点不是把一行 JSON `JSON.parse` 出来，而是 stdout 是字节流，chunk 边界不等于消息边界。一条 JSON 可能被拆成多个 chunk，也可能一个 chunk 里有多条 JSON。`JsonlDecoder` 按换行累计字节，完整一行后再解析，并限制单帧大小，防止异常输出导致无界内存增长。

解析失败、超大 frame、EOF 和 stderr 都要分别处理。stdout 是协议通道，stderr 是诊断通道，不能把 stderr 混进 JSONL 解析。

### 继续追问：如果 JSON 中有换行怎么办？

答题要点：

- 协议层发送的是 JSON 编码后的单行 frame，字符串内部换行会被转义为 `\\n`。
- 解码器只按真实的换行字节分帧，再对完整 frame 做 JSON 解析。
- 不用逐 chunk 解析，也不手动按字符拼接完整对象。

### 继续追问：如何处理半包、粘包和超大消息？

答题要点：

- 半包：保留未完成字节，等下一次 `data`。
- 粘包：循环取出同一 chunk 中的多个换行分隔 frame。
- 超大消息：累计长度超过限制时抛出 `JsonlFrameTooLargeError`，结束当前协议连接或 Runtime，记录诊断。
- 每条日志还有独立长度限制，避免 stderr 或日志队列无限增长。

### 继续追问：RPC 请求和事件如何对应？

答题要点：

- 请求有明确的 request id，Main 维护待处理请求表。
- 收到带 id 的响应时 resolve 对应 Promise。
- 没有对应 id 的消息按 Runtime event 处理。
- Runtime 退出、协议错误或超时时，要拒绝所有未完成请求，不能让 Promise 永远 pending。

### 问题 4：流式输出为什么需要 reducer，而不是直接 append 文本？

### 建议回答

OMP 的事件包含累计快照、工具开始/进度/结束、Thinking、权限请求和最终消息。直接 append 会造成累计文本重复、工具卡片重复、事件乱序时状态倒退。

Renderer 使用 `omp-event-reducer.ts` 把原始事件投影为稳定的 `ConversationProjection`。对 `message_update` 按消息 id 替换累计快照；对 Tool Call 按 `toolCallId` 归并；对完成状态设置终态，忽略终态之后的旧进度；保留文本、工具和最终回答的原始顺序。

### 继续追问：`message_update` 为什么是替换，不是追加？

答题要点：

- 事件中的 `message.content` 是截至当前的累计快照，例如“你”后面是“你好”。
- 如果把两次文本都追加，结果会变成“你好你”。
- Reducer 按 message id 找到对应项，用新快照替换旧内容。
- 测试明确验证最终只保留“你好”。

### 继续追问：Tool Update 先到、Tool Call 后到怎么办？

答题要点：

- 先按 `toolCallId` 建立临时 Action。
- 后到的 Tool Call 补充名称和参数，不重新生成第二张卡片。
- 同一个 id 的 start、update、end 始终归并到一个 action。

### 继续追问：如何处理乱序和重复事件？

答题要点：

- 以稳定 id 作为归并键，而不是以数组位置作为依据。
- Action 已经 ended 后，旧 update 不得把状态改回 running，也不能覆盖最终结果。
- 重复 start、重复 end 要保持幂等或至少不产生重复 UI 项。
- 对无法匹配的异常事件保留诊断信息，但不能让整个 Renderer 崩溃。

### 继续追问：为什么要区分过程文本和最终文本？

答题要点：

- Agent 可能先输出说明，再调用工具，最后输出总结。
- UI 需要保留过程发生的顺序，但默认只突出最终回答。
- Reducer 记录 `finalItemIds`，只有正常 `stop` 且存在非空最终文本时才标记最终项。
- `length`、`error`、`aborted` 不误标为完整最终回答。

## 五、Workspace、Session 与数据一致性

### 问题 5：Workspace 和 Session 数据放在哪里，如何恢复？

### 建议回答

Desktop 自己保存 Workspace 元数据、置顶/归档状态、当前选择、草稿和 Runtime 配置；OMP 自己管理 Provider 凭据和 Session JSONL。Desktop 不读取或保存 Provider Token。

启动时 Main 读取 Desktop 状态，恢复上次 Workspace、Session、草稿和 Runtime 网络配置。Session 列表通过扫描 OMP 的 session 文件、解析头部和可见消息得到。旧 Session 分页加载，不把全部历史一次性放进 Renderer。

### 继续追问：为什么不让 Desktop 再维护一套完整 Session 数据库？

答题要点：

- OMP 已经是 Session 的真实来源，复制一份会产生双写和同步问题。
- Desktop 只保存展示和导航需要的元数据，Session 内容按 OMP 格式读取。
- 写消息仍通过 RPC，让 OMP 统一维护会话格式和压缩逻辑。

### 继续追问：新建 Session 时如何避免“列表有了但第一条消息丢失”？

答题要点：

- 新 Session、Runtime 切换、第一条 prompt 和 Session 文件写入存在时序竞争。
- 处理上要区分“Session 已创建”“Runtime 已切换”“消息已发送/已落盘”几个状态，不能只看 UI 选中状态。
- 测试覆盖空新 Session 历史 race 和第一条消息持久化 race。
- 如果恢复列表时文件还没写完，应等待或重试读取，而不是把空文件当作最终结果。

### 继续追问：历史消息很多时怎样控制性能？

答题要点：

- Session 列表按批次读取，旧记录每批 50 条。
- `@session` 不把完整历史放进上下文，只返回压缩摘要、首条用户消息和最近可见对话，更早内容分页读取。
- Renderer 对历史和实时流使用同一套投影模型，但流式更新只替换活动消息，不复制旧快照。
- 测试用 1,000 条历史和 6,000 个累计快照验证处理耗时和活动对象大小。

### 问题 6：如果切换 Session 时当前任务还在运行怎么办？

### 建议回答

可以直接切换可见 Session。原任务继续在它已绑定的 Runtime 中后台运行，不会因界面切换被停止。Main 按目标 Session 路由后续请求和事件，Renderer 分别保存各 Session 的对话投影和运行状态。需要停止后台任务时，使用该 Session 的“停止任务”，不影响其他 Runtime。

## 六、文件上下文与路径安全

### 问题 7：`@file`、`@folder` 和 `@session` 是怎么实现的？

### 建议回答

输入框中的 `@` 只做候选选择，不把文件正文复制到 Renderer 或 Prompt 中。候选只搜索当前 Workspace，文件和目录最终交给 OMP 的现有工具按路径读取。Desktop 保存的是引用描述和相对路径。

`@session` 比较特殊：Main 注册只读的 `omp-session://<workspace-id>/<session-id>` Host URI。Main 校验 Workspace、Session 和实际路径后，按页返回摘要、首条消息和最近可见对话。这样能减少上下文体积，也不让 Renderer 直接读任意 Session 文件。

### 继续追问：如何防止 `../` 路径越过 Workspace？

答题要点：

- 输入路径先规范化，再解析绝对路径。
- 用 `relative(root, candidate)` 判断候选是否仍在 Workspace 根目录内。
- 拒绝以 `..` 开头、绝对路径越界、符号链接解析后越界的引用。
- Session 引用同时校验 Workspace id、Session id、Session 文件头和实际 session 目录。

### 继续追问：为什么不直接把文件内容塞进 Prompt？

答题要点：

- 会增加 Desktop 内存和 IPC 传输量。
- 大文件、二进制文件、图片和目录会带来解析、截断和安全问题。
- OMP 已有文件读取工具，Desktop 只需要提供准确的相对路径。
- 让 Agent 按需读取，也更容易控制上下文大小。

### 继续追问：草稿恢复时会不会把引用内容一起保存？

答题要点：

- 只保存文字和 `@` 引用描述，不复制引用正文。
- 单项草稿最多 256 KiB，全部草稿合计最多 2 MiB。
- 过期草稿会清理；直接粘贴的图片附件只在本次运行保留，不跨重启恢复。

## 七、权限、登录与 Electron 安全

### 问题 8：Agent 要执行命令时，权限确认怎么走？

### 建议回答

OMP Runtime 发出 Extension UI 或 Permission 请求。Main 接收后先根据请求类型处理敏感字段，再通过 IPC 发给 Renderer 展示。用户的选择通过 Preload 回到 Main，Main 校验请求仍然存在后，再转成 RPC response 发回 Runtime。

权限模式有 `always-ask`、`write` 和 `yolo`。它影响请求是否需要用户确认，但不能让 Renderer 直接执行命令。MVP 不注册 Host Tools，普通 Renderer 也不直接调用 RPC `bash`；Agent 的 Bash 仍由 OMP Runtime 执行。

### 继续追问：为什么 OAuth URL 不直接发给 Renderer？

答题要点：

- URL 可能带 callback code、state 或其他敏感信息。
- Main 收到 `open_url` 请求后通过系统默认浏览器打开，Renderer 只收到脱敏后的状态。
- 用户输入也从 Renderer 回到 Main，再由 Main 转成 RPC response，日志中不记录原文。
- 测试验证 Renderer payload 不包含私密 URL、API key 和用户输入。

### 继续追问：Electron 做了哪些安全设置？

答题要点：

- 开启 context isolation，不向页面暴露 Node 环境。
- Renderer 使用 CSP 限制脚本、连接和资源来源。
- 外部链接通过 Main 的白名单/安全入口交给系统浏览器处理。
- 不为了绕过兼容问题默认开启 `--no-sandbox`。
- 本地文件操作在 Main 做路径校验，Renderer 只拿到必要结果。

### 继续追问：如果 Renderer 被注入恶意脚本，能不能执行任意命令？

答题要点：

- 它不能直接拿 Node、`child_process` 或文件系统 API。
- Preload 只暴露固定方法，不能调用任意 IPC channel。
- Main 仍需对 Workspace、Session、路径、请求 id 和参数做二次校验；不能把“Preload 有类型”当成安全边界。
- Prompt 本身可以让 Agent 请求 Bash，但是否执行由 OMP Runtime 的权限模型和用户确认决定。

## 八、Runtime 环境、代理与 Linux 兼容

### 问题 9：为什么图形界面启动时 Runtime 可能找不到命令？

### 建议回答

终端启动和桌面启动得到的环境不一定相同。图形启动器可能没有用户 Shell 初始化的 PATH、代理变量或工作目录。因此 Main 启动 Runtime 前会解析环境，至少诊断 `which omp`、`which git`、`which node`、`which python`、PATH 和 Workspace，然后通过 `spawn` 的 `env` 显式传入。

代理是 Runtime 的启动配置，不是 Electron 全局代理。支持关闭、自动和手动三种模式。关闭时显式删除大小写代理变量；自动模式读取 Login Shell 的 HTTP 代理变量，必要时探测本地 v2rayN HTTP 入站；手动模式生成本机 HTTP 代理地址。环境或网络配置改变后重启 Runtime。

### 继续追问：为什么不直接修改 `process.env`？

答题要点：

- `process.env` 是 Electron 主进程全局环境，修改会影响不应使用 Runtime 代理的其他逻辑。
- 目标是只影响 OMP Runtime 及其子进程。
- `spawn({ env })` 能明确表达最终环境，便于测试、诊断和清除代理变量。

### 继续追问：关闭代理能保证绕过 VPN/TUN 吗？

答题要点：

- 不能。关闭代理只保证删除显式 HTTP/HTTPS/ALL_PROXY 等环境变量。
- TUN 或操作系统路由层的流量接管不由这些变量控制。
- 产品文档明确区分“没有注入代理”和“绕过系统路由”。

### 继续追问：为什么手动代理目前只支持本机 HTTP？

答题要点：

- MVP 先覆盖本地代理工具常见的 HTTP 入站，避免引入认证凭据存储和远程代理安全风险。
- Host 固定为回环地址，端口范围校验为 1～65535。
- SOCKS5 不能只依赖环境变量保证 OMP/Bun Provider fetch 的完整支持，所以不把它伪装成已支持能力。
- 未来有明确需求时，再扩展协议、认证和 Workspace 级配置。

### 继续追问：Wayland 和 GPU 问题怎么处理？

答题要点：

- 正式验收环境是 Ubuntu x64、原生 Wayland 和 NVIDIA RTX 3090。
- 运行时设置 Linux 输入法相关选项，兼容 Wayland 下的中文输入。
- GPU 有默认硬件加速路径和 `--disable-gpu` 诊断路径。
- CI 做 headless/smoke，发布前还要做真实 GPU 验收，检查 GPU Feature Status、首屏截图、Runtime ready、退出和遗留进程。
- 不默认推荐 `--no-sandbox`；AppImage 如果受系统 sandbox 策略影响，要给出明确诊断并建议 `.deb`。

## 九、性能与资源控制

### 问题 10：这个项目里你关注哪些性能问题？怎么验证？

### 建议回答

主要关注三类：流式事件处理不能随历史增长而变慢；日志和 stderr 不能无限积压；Runtime 和 Electron 不能导致空闲 CPU、内存持续增长。

流式 reducer 对累计消息做原地语义上的替换，只保留活动快照，不把每个历史版本都存下来。测试使用 1,000 条历史、6,000 个流事件验证批次 P95；Renderer 测试还用 Profiler 检查 React 提交和渲染耗时。

日志有队列上限、单条长度上限和滚动文件数量上限，过载时丢弃普通日志但累计丢弃数量和字节数。发布验收会测空闲 CPU、PSS、长时间流式输出、100 MB stderr、Stop 响应和退出清理。

### 继续追问：为什么不把所有事件存进数组，最后再渲染？

答题要点：

- 长对话和长时间流式输出会导致数组、序列化和 React diff 持续增长。
- UI 需要的是当前可见投影，不是所有中间快照的完整副本。
- 原始 Runtime 日志仍保留在 Main 的诊断日志中，Renderer 不承担日志仓库职责。

### 继续追问：日志过载时丢日志会不会影响排障？

答题要点：

- 普通重复进度日志可以丢，协议错误、Runtime 退出和权限结果不能静默丢失。
- 过载时记录丢弃条数和字节数，恢复后写一条汇总。
- 日志有明确上限，优先保证应用仍能 Stop 和退出。
- 关键状态通过结构化 Runtime event 维护，不依赖全文日志恢复 UI。

### 继续追问：你怎么判断性能测试可信？

答题要点：

- 单元性能测试用于防止算法退化，不等于真实机器发布验收。
- 发布基准固定机器、Wayland、分辨率、GPU 和电源模式，冷启动和热启动各测多次并记录中位数。
- 真实模型验收、fake Runtime 压力测试和 GPU 验收分开，避免网络波动掩盖 Renderer 或进程问题。
- 指标和阈值写入 `docs/release-acceptance.md`，不能只凭主观感觉。

## 十、测试与故障定位

### 问题 11：项目测试怎么分层？哪些测试最有价值？

### 建议回答

测试分为纯函数、Main、Renderer 和集成 smoke。

- 纯函数：JSONL 解码、环境和代理解析、路径校验、状态转换。
- Main：Runtime Supervisor、Runtime IPC、Session Catalog、文件操作、权限和日志脱敏。
- Renderer：事件 reducer、对话线程、Workspace/Session UI、文件树和模型控制。
- smoke：fake Runtime 的 RPC 链路、Electron 启动、打包检查和真实 OMP 的无凭据 ready/get_state 检查。

最有价值的不是只测“能显示一条消息”，而是测边界：半包 JSON、乱序 Tool event、Renderer 重载时未完成的权限请求、切换 Workspace race、代理变量清除、OAuth 敏感信息不泄露，以及 Runtime 退出后未完成请求不会永久挂起。

### 继续追问：为什么需要 fake Runtime？

答题要点：

- 真实模型请求慢、不稳定、有凭据和费用问题，不适合做高频回归。
- fake Runtime 可以精确控制事件顺序、延迟、错误、stderr 大小和退出时机。
- 它适合验证协议、状态机、压力和 Stop/退出行为。
- 真实 OMP smoke 仍然保留，用于检查 bundled Runtime 的基本兼容性。

### 继续追问：如果测试通过但线上仍然出问题，你怎么定位？

答题要点：

1. 先看 Runtime 状态和退出码，确认是 UI、IPC 还是 OMP 进程问题。
2. 看 Main 脱敏日志和 Runtime stderr，区分环境、网络、协议和模型错误。
3. 看事件序列：是否丢了 start/end、是否 id 重复、是否旧 Runtime 事件进入新 Session。
4. 用最小 Workspace 和 fake Runtime 复现时序，再补回归测试。
5. 如果只在 Linux 出现，再比较启动环境、Wayland/X11、GPU、代理和打包资源。

### 继续追问：为什么不只做端到端测试？

答题要点：

- 端到端测试能验证主链路，但很难稳定制造半包、乱序和进程退出时机。
- 纯函数和模块测试能快速定位状态转换错误。
- 两者结合：模块测试保证边界规则，smoke 保证真实装配和启动链路。

## 十一、打包、版本和发布

### 问题 12：Linux 打包时为什么把 OMP 放在 ASAR 外？

### 建议回答

Main、Preload、Renderer 和应用资源放在 `app.asar` 内；OMP 是需要被 `spawn` 执行的二进制，作为 extra resource 放到 `resources/runtime/omp`，这样可以直接校验文件存在、架构和 `0755` 权限。

OMP 版本、下载地址和 SHA-256 集中在 `runtime/manifest.json`。构建前下载并校验固定版本，失败就停止，不回退到 latest 或本机未知版本。首个发布目标是 Ubuntu 22.04/24.04 x64，产出 AppImage 和 `.deb`。

### 继续追问：升级应用后用户数据会不会丢？

答题要点：

- Workspace、Session、Runtime 环境和网络设置放在用户数据目录，不放在安装目录。
- `.deb` 卸载只删除应用，不删除用户主目录中的状态、日志、Session 或 OMP 配置。
- 通过同版本重装和跨版本升级验收确认恢复能力。
- 不正式支持降级；如果旧版本无法读取新数据，应报错而不是静默重置。

### 继续追问：AppImage 和 `.deb` 怎么取舍？

答题要点：

- AppImage 便携，下载后赋予执行权限即可运行，但可能受系统 sandbox/FUSE 环境影响。
- `.deb` 更符合 Ubuntu 系统安装方式，能由 apt 处理系统依赖，需要管理员权限安装和卸载。
- 两种格式都发布，不能把一种格式的成功当成另一种格式的验收结果。

### 继续追问：如何保证产物里的 Runtime 没被替换？

答题要点：

- 下载脚本读取固定 manifest，校验 SHA-256 和架构。
- 打包检查验证 Runtime 文件存在、路径正确、权限正确。
- CI 同时跑 fake Runtime smoke 和真实 OMP 无凭据 smoke。
- 产物生成后检查应用版本、Deb 元数据和文件名一致。

## 十二、设计取舍与反事实问题

### 问题 13：这个项目最重要的一个设计取舍是什么？

### 建议回答

最重要的取舍是复用 OMP Runtime，而不是在 Desktop 内重新实现 Agent Loop。这样可以减少重复代码，保持 Provider、模型、工具和 Session 行为的一致性；代价是 Desktop 必须认真处理 RPC 协议、Runtime 进程、环境变量、错误和版本兼容。

另一个取舍是 MVP 只允许一个活动 Session 生成。它牺牲了并行能力，但让 Runtime 生命周期、Follow-up、Stop、权限请求和 Session 切换更容易证明正确。并行能力可以在后续引入 Runtime 池和并发上限，而不必一开始把所有状态复杂度带进来。

### 继续追问：如果现在让你重做，你会改什么？

答题要点：

- 会继续保留 Main 管 Runtime、Preload 窄桥接和 Renderer reducer 这三个边界。
- 会更早把 Runtime 生命周期建模成显式状态机，并给每次启动分配 generation/token，所有异步结果都检查 generation，减少旧进程事件污染的风险。
- 会更早统一结构化错误码和诊断 id，方便从 UI 错误定位到 Main 日志。
- 不会为了未来并行 Session 过早引入 Runtime 池；先用真实压力和使用场景确认需求。

### 继续追问：如果 OMP RPC 协议变了怎么办？

答题要点：

- 把协议解码、请求映射和事件 reducer 分开，避免 OMP 字段直接散落在 UI 组件。
- Runtime ready 后读取版本或能力信息，必要时做能力判断。
- 固定 bundled OMP 版本，Desktop Release 和 Runtime 一起验收，减少不受控的版本组合。
- 新事件先兼容忽略或显示通用状态，涉及安全和数据一致性的未知请求必须拒绝并记录。

### 继续追问：为什么不用 Redux、Zustand 或数据库？

答题要点：

- 当前状态规模可以由 Main 的状态模块、Renderer React state/reducer 和文件持久化承担。
- 对话流的关键是事件归并规则，不是引入更大的状态库。
- Desktop 状态量有限，直接 JSON 文件便于迁移、备份和调试；Session 仍由 OMP 管理。
- 如果后续出现多窗口、复杂离线同步或大量实体查询，再评估数据库或专门状态库。

## 十三、面试结束前可以主动说的验证结果

如果面试官问“你怎么证明它能工作”，可以按下面顺序回答：

1. `pnpm typecheck`：检查 Main、Preload、Renderer 的共享类型。
2. `pnpm lint` 和 `pnpm format:check`：检查代码质量和格式。
3. `pnpm test`：运行 JSONL、Runtime、Session、路径、权限、Reducer 和 UI 测试。
4. fake Runtime smoke：验证 RPC 链路、流式事件、错误和退出。
5. Electron smoke：验证窗口启动、Renderer ready、Runtime ready 和退出清理。
6. `pnpm build`、Linux package check：验证构建产物和 bundled Runtime。
7. 发布前的真实 Wayland/GPU 验收：验证黑屏、输入法、流式对话、Thinking、Tool Call、Permission、Stop、退出和性能。

不要说“所有环境都验证过”。当前正式真实 GPU 验收范围是 NVIDIA RTX 3090、原生 Wayland、Ubuntu x64；Intel、AMD 和 X11 不属于本次正式验收范围。

## 十四、面试时的简短收尾

这个项目的核心不是把一个聊天框做出来，而是把一个本地 Agent Runtime 安全、稳定地接到桌面 UI 上。我的实现重点是进程边界、协议事件归并、状态恢复和 Linux 运行环境。对于暂未实现的并行 Session、Diff 和编辑器，我保留了清楚的边界，没有在 MVP 中提前引入复杂度。
